release notes (see `docs/CLIENT_RELEASE_NOTES_TEMPLATE.md`).

## 2. Repository Structure

The project already has a clear, working structure. **It is deliberately not reorganised** into
`frontend/ backend/ database/` folders: moving `src/` or `server/` would break the Vite build, the esbuild
server bundle, the deploy packager and every import, with no maintainability gain.

| Concern | Location |
|---|---|
| Frontend (React SPA + admin dashboard) | `src/` (`src/admin/` = CMS, `src/pages/`, `src/components/`, `src/services/`, `src/data/`, `src/i18n/`) |
| Backend (Express API) | `server/` (`server/index.ts` entry, `server/api.ts`, `server/auth.ts`, `server/supportApiRoutes.ts`, `server/services/`, `server/storage/`) |
| Database | `server/database/` (`migrations/*.sql`, adapters, `repositories/`) |
| Static assets | `public/` |
| Scripts, operational tests | `scripts/` (migrations, smoke/API tests, packaging, `check-release.mjs`) |
| Documentation | `docs/` (process docs, release records in `docs/releases/`) |
| CI / GitHub | `.github/` (workflows, PR template) |
| Build outputs (not edited by hand) | `dist/`, `server.js` (generated by `npm run build`) |
| Infrastructure | No infrastructure-as-code exists. Hosting is configured in Hostinger hPanel; settings are documented in `.env.example` and `docs/RELEASE_PROCESS.md`. |

Recommended later clean-up (not required for the workflow): move the root-level SEO/Hostinger report
files into `docs/archive/`, and stop committing the generated `server.js` once deployments build it.

## 3. Branching Strategy

```
main ─────────●───────────────●──────────●───────▶  production-ready, tagged releases (v1.0.0, v1.1.0 …)
               \             ↑ release PR  ↑ hotfix PR
staging ────────●───●───●────●─────────────●─────▶  integration + QA
                   ↑   ↑                    ↑ (hotfix merged back)
feature/*  ───────●   │
bugfix/*   ───────────●
hotfix/*   ──────────────────────────(from main)──▶
```

| Branch | Purpose | Created from | Merges into | Lifetime |
|---|---|---|---|---|
| `main` | Production-ready code. Every production release is a tag on `main`. | — | — | permanent |
| `staging` | Pre-production integration and QA. Everything for the next release lands here first. | `main` | `main` (release PR) | permanent |
| `feature/<id>-<slug>` | New functionality | `staging` | `staging` | until merged |
| `bugfix/<id>-<slug>` | Normal (non-urgent) bug fixes | `staging` | `staging` | until merged |
| `hotfix/<id>-<slug>` | Critical production fixes that cannot wait for the next release | `main` | `main`, then merged back into `staging` | until merged |
| `release/vX.Y.Z` | *Optional.* Only for a large release that needs stabilisation while new work continues on `staging` | `staging` | `main` (+ back into `staging`) | until released |

Naming examples: `feature/ZAN-024-editable-homepage`, `bugfix/ZAN-031-mobile-nav`,
`hotfix/ZAN-040-admin-login`, `release/v1.2.0`. Lower-case, hyphen-separated, task ID first.

Normal flow:

```
feature/*  →  PR into staging  →  automated build + checks  →  QA on staging  →  client approval (if required)
          →  release PR staging → main  →  tag vX.Y.Z  →  deploy to production  →  release notes to Zanzirangi
```

Rules:
1. Nobody commits directly to `main`. `main` only changes through a release PR or a hotfix PR.
2. `staging` only changes through PRs from `feature/*`, `bugfix/*` and `hotfix/*` back-merges.
3. Never force-push `main` or `staging`; never rewrite published history; never delete or move a tag.
4. Delete short-lived branches after merging (on GitHub); keep `main` and `staging`.
5. Merge strategy:
   - `feature/*`, `bugfix/*` → `staging`: **Squash and merge**. The squash commit title is the PR title in Conventional Commit format and includes the PR number, e.g. `feat(cms): add editable homepage sections (#42)`.
   - `staging` → `main` and `hotfix/*` → `main`: **Create a merge commit** (no squash), so every individual change stays traceable on `main`.

### Branch protection — status

Verified through the GitHub API on 2026-10-01: `main` is **not protected**, and no `staging` branch exists on GitHub yet.
**Branch protection requires external GitHub configuration.** Recommended settings for `main` and `staging`:
- Require a pull request before merging (1 approval for `main`).
- Require status check **CI / build** to pass.
- Block force pushes and branch deletion.
- Require linear history: off (merge commits are used on `main`).

## 4. Commit Convention — Conventional Commits

Format:

```
<type>(<optional scope>): <short summary in imperative mood, lower case, no period>

<optional body: what changed and WHY>

Refs: ZAN-024
```

| Type | Use for | Version impact |
|---|---|---|
| `feat` | New functionality visible to guests or admins | MINOR |
| `fix` | Bug fix | PATCH |
| `perf` | Performance improvement | PATCH |
| `refactor` | Code change without behaviour change | none / PATCH |
| `style` | Formatting or purely visual tweak without logic change | PATCH |
| `docs` | Documentation only | none |
| `test` | Tests only | none |
| `build` | Build system, dependencies, packaging | none / PATCH |
| `ci` | CI configuration | none |
| `chore` | Maintenance with no production impact | none |
| `revert` | Reverts a previous commit (`revert: feat(cms): …` + `This reverts commit <hash>.`) | depends |

Breaking changes: add `!` after the type (`feat(api)!: …`) **and** a `BREAKING CHANGE:` footer explaining
the impact and migration. Breaking changes trigger a MAJOR version.

Suggested scopes: `cms`, `admin`, `auth`, `api`, `db`, `media`, `chat`, `seo`, `i18n`, `ui`, `deploy`, `release`.

Examples:

```
feat(cms): add editable homepage sections
fix(auth): resolve admin login redirect
docs: update deployment documentation
refactor(auth): simplify authentication middleware
perf(ui): optimize homepage assets
test(cms): add CMS integration tests
ci: run release check on pull requests
fix(db)!: rename villa price column
```

Commit hygiene:
- Never commit `.env`, `.env.*` (except `.env.example`), `server/data/db.json`, `backups/`, `uploads/`, deploy zips, or any credential. These are listed in `.gitignore`. Check `git status` before every commit.
- Never paste database hosts, usernames, IP addresses or passwords into commits, PRs or docs. **The GitHub repository is currently public.**
- One logical change per commit; the message explains *why*, not only *what*.

## 5. Pull Requests

Every change reaches `staging` and `main` through a PR using `.github/pull_request_template.md`. The PR records:
- the business requirement and task ID (`ZAN-###`);
- changes, testing performed, security checks;
- deployment impact (environment variables, database migration, rollback);
- client impact (none / visible improvement / client approval required).

The reviewer is a TKS engineer other than the author whenever possible. The reviewer checks code, the PR
checklist, and that CI passed.

## 6. Traceability — answering "what, when, who, why, which version, is it live?"

```
Business request (Zanzirangi)  →  Task ZAN-###  →  Branch feature/ZAN-###-slug  →  Commits "…  Refs: ZAN-###"
→  PR #N (into staging)  →  QA on staging  →  Release PR staging → main  →  Tag vX.Y.Z
→  Production deployment (docs/releases/DEPLOYMENT_LOG.md)  →  Client release notes vX.Y.Z
```

| Question | Where the answer lives |
|---|---|
| What changed? | `CHANGELOG.md`; PR description; `git log vA..vB` |
| When did it change? | commit and merge dates; release date in `CHANGELOG.md`; deployment date in `DEPLOYMENT_LOG.md` |
| Who changed it? | commit author; PR author and reviewer; "Deployed by" column in `DEPLOYMENT_LOG.md` |
| Why was it changed? | task `ZAN-###` → business request; PR "Business Requirement"; commit body |
| Which version contains it? | `git tag --contains <commit>`; the version heading in `CHANGELOG.md` |
| Is it live in production? | last row of `docs/releases/DEPLOYMENT_LOG.md`; admin dashboard "System Version"; `GET /api/health` → `version` |

Example:

| Step | Value |
|---|---|
| Request | "Zanzirangi needs editable homepage content." |
| Task | ZAN-024 |
| Branch | `feature/ZAN-024-editable-homepage` |
| Commit | `feat(cms): add editable homepage sections` + `Refs: ZAN-024` |
| Pull request | PR #42 → `staging` |
| Release | v1.3.0 (tag on `main`) |
| Production | Deployed 2026-11-02 (DEPLOYMENT_LOG row) |
| Client note | "Zanzirangi Website Update v1.3.0" |

Until a task tracker is agreed, TKS keeps task IDs as **GitHub Issues** titled `ZAN-### <summary>`
(issues are enabled on the repository). If another tracker is adopted, keep the `ZAN-###` key format.

## 7. Useful Commands (safe, read-only unless noted)

```bash
git status
git branch -a
git tag --list "v*"
git log --oneline --decorate --graph -n 50
git log v1.0.0..v1.1.0 --oneline          # changes between two releases
git tag --contains <commit>               # which release contains a commit
git describe --tags --abbrev=0            # latest release tag reachable from HEAD
```

Starting work (creates a branch, no impact on others):

```bash
git switch staging && git pull
git switch -c feature/ZAN-024-editable-homepage
```
